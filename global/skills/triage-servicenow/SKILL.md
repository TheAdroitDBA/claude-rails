# Triage ServiceNow Queue

Pull the DBA Operations unassigned queue, classify each ticket, distribute the real work evenly across the active team, and track the clean-inbound streak.

See `triage-servicenow.feature.md` for criteria and `triage-servicenow.flow.md` for the pipeline.

## Prerequisites

- **servicenow-api skill** -- handles ServiceNow auth, queries, and updates. This skill orchestrates it; it does not duplicate auth.
- **Manager-app DB** -- `C:\code\ClientSetup\DBALeadership\Management\app\data\dba_management.db`, table `people`. Roster source of truth.
- **Solutions store directory** -- `C:\code\ClientSetup\DBALeadership\Management\ServiceNowSolutions\`. Create if missing.
- **Assignment group in scope** -- "DBA Operations" (single group, all regions).

## Procedure

### Step 1 -- Fetch the queue

Use the `servicenow-api` skill to query tickets in assignment group "DBA Operations" where `assigned_to` is empty AND state is active (not closed / not resolved). Pull fields: `number`, `short_description`, `description`, `opened_at`, `caller_id`, `category`, `priority`.

If the API call returns 401 or fails to reach the host, raise `ServiceNowAuthExpired` or `ServiceNowUnreachable` respectively and abort. Do not silently treat as empty queue.

If the queue is empty, report "DBA Operations queue is empty -- nothing to triage" and skip to Step 10 (still update the streak with REROUTE count = 0 for today).

### Step 2 -- Load the active roster

Query the manager-app DB for active direct reports (Jeremy's team), including the cached ServiceNow sys_id:

```powershell
& "C:\code\ClientSetup\DBALeadership\Management\app\.venv\Scripts\python.exe" -c "import sqlite3; c=sqlite3.connect(r'C:\code\ClientSetup\DBALeadership\Management\app\data\dba_management.db'); [print(r) for r in c.execute('SELECT id,name,email,servicenow_sys_id FROM people WHERE manager_id=14 AND is_active=1 ORDER BY name')]"
```

If zero active members come back, raise `RosterEmpty` and abort -- do not proceed to distribution.

**Resolve missing sys_ids (self-healing):** for any roster row where `servicenow_sys_id` is NULL, use the `servicenow-api` skill to look up `sys_user` by email, then write the resolved sys_id back to the people table:

```sql
UPDATE people SET servicenow_sys_id = ? WHERE id = ?;
```

This happens once per person, then the cached value is used on all subsequent runs. If the email lookup returns nothing (person has no ServiceNow account), surface it in the report as a setup gap and exclude them from the ASSIGN bucket for this run -- do not abort the whole run.

### Step 3 -- Load the common-solutions library

Read `C:\code\ClientSetup\DBALeadership\Management\ServiceNowSolutions\common-solutions.json` through the load_solutions seam. Schema:

```json
{
  "solutions": [
    {
      "id": "uuid-or-slug",
      "pattern": "natural-language description of what this matches",
      "match_keywords": ["keyword1", "keyword2"],
      "recommended_steps": "what to do to resolve in <=5 min",
      "added_date": "YYYY-MM-DD",
      "times_matched": 0
    }
  ]
}
```

If the file does not exist, treat as `{"solutions": []}` and continue. Library starts empty by design -- it grows via Step 9.

### Step 4 -- Classify each ticket

For each ticket from Step 1, evaluate in this order:

1. **REROUTE check first.** Read `short_description` and `description`. Does the ticket clearly belong to another team? Use these heuristics (conservative -- when in doubt, do NOT mark REROUTE):
   - Pure Active Directory / identity / SSO issues (no SQL Server component) -> Identity team
   - Pure network / firewall / DNS issues (no SQL Server component) -> Network team
   - Application-layer bugs that mention an app name but no database symptom -> App team
   - Workstation / desktop / user-machine issues -> Desktop Support
   - The ticket is auto-generated by an alert that should have routed elsewhere
   
   When marking REROUTE, record a recommended target assignment group. If the target is genuinely unclear, mark as `REROUTE-UNKNOWN` (still counts against the streak per Step 10).

2. **QUICK-FIX match.** If not REROUTE, scan the solutions library. A ticket matches a solution when its description/short_description contains the solution's `match_keywords` (case-insensitive substring is fine for v1; refine later). On match, attach the solution's recommended_steps to the ticket and increment its `times_matched` counter in memory (persist at end of run).

3. **ASSIGN.** If neither REROUTE nor QUICK-FIX, the ticket is real DBA work -> ASSIGN bucket.

### Step 5 -- Distribute the ASSIGN bucket

Order ASSIGN tickets by priority (highest first), then by opened_at (oldest first). Round-robin them across the active roster. The constraint: after distribution, the max-min spread of assignments per person within this run must be at most 1.

Simple algorithm that satisfies this: sort roster by current load (ascending), assign one ticket to the lightest-loaded person, recompute load, repeat. With equal starting loads, this is round-robin.

### Step 6 -- Render the plan

Generate a Markdown report at `C:\code\ClientSetup\DBALeadership\Management\Transcripts\adhoc\ServiceNowTriage_YYYY-MM-DD.md`. Structure:

```markdown
# DBA Operations Triage -- YYYY-MM-DD

Total tickets: N
- QUICK-FIX: A
- REROUTE: B (UNKNOWN: C)
- ASSIGN: D

Clean-inbound streak: E days (resets to 0 if B > 0 today)

## QUICK-FIX (A)
- INC0123456 -- [short description] -- matched: [pattern name]
  Recommended steps: ...

## REROUTE (B)
- INC0123457 -- [short description] -- target: [Network team / UNKNOWN]
  Reason: ...

## ASSIGN
### [Person Name] (X tickets)
- INC0123458 -- P3 -- [short description]
- INC0123459 -- P4 -- [short description]

### [Next Person] (X tickets)
...
```

### Step 7 -- Confirm with user (dry-run is default)

Present the report. Ask: "Apply this plan? (y/N)". Default is no. If the user does not explicitly confirm, stop here -- this is dry-run mode and the run is complete (still update the streak in Step 10).

### Step 8 -- Apply (only on explicit confirm)

For each ticket:
- **QUICK-FIX:** do nothing automatically. The user will apply these manually. After running them, they can invoke Step 9 to capture new patterns.
- **REROUTE:** update `assignment_group` to the recommended target group (skip if `REROUTE-UNKNOWN`). Add a work note explaining the routing decision.
- **ASSIGN:** update `assigned_to` to the matched roster member's cached `servicenow_sys_id` (from Step 2). Add a work note: "Assigned via triage-servicenow YYYY-MM-DD". If a roster member has no sys_id even after the Step 2 resolve attempt, do NOT assign tickets to them on this run -- they were already excluded from the ASSIGN bucket.

Use the `servicenow-api` skill for the writes. If any write fails, stop the batch, report which succeeded and which did not, and preserve the report so the user can retry the failures.

Also persist the in-memory `times_matched` updates back to `common-solutions.json` via the save_solutions seam.

### Step 9 -- Capture new solutions (optional, on user prompt)

After the user has applied a quick fix that did NOT match an existing solution, prompt: "Capture this as a reusable pattern?". On yes, ask for:
- A short pattern name
- Match keywords (comma-separated)
- The recommended steps (can paste from what they just did)

Append the entry to `common-solutions.json` with `times_matched: 0`, today's date, and a generated id.

### Step 10 -- Update the clean-inbound streak

Read `C:\code\ClientSetup\DBALeadership\Management\ServiceNowSolutions\streak.json`. Schema:

```json
{
  "current_streak_days": 0,
  "last_clean_date": "YYYY-MM-DD",
  "last_reset_date": "YYYY-MM-DD",
  "history": [
    {"date": "YYYY-MM-DD", "reroute_count": 0, "streak_after_run": 1}
  ]
}
```

Rules:
- If REROUTE count for today's run > 0: set `current_streak_days = 0`, set `last_reset_date = today`.
- Else if today is already in history as a clean day: no change (don't double-count multiple runs in one calendar day).
- Else: `current_streak_days += 1`, `last_clean_date = today`.

Append the run's outcome to `history` (keep the last 90 entries; trim oldest).

If the file is missing or corrupt: log a warning, recreate it fresh, set `current_streak_days = 0` if any REROUTE today or `1` otherwise.

**Phase 2 handoff trigger:** when `current_streak_days` reaches 30, surface a banner in the report: "**CLEAN-INBOUND STREAK = 30. Phase 2 handoff is due. Name the Lead/Senior who takes over.**"

## Output format reference

The Markdown report from Step 6 is the user-facing artifact. Keep it scannable: counts at the top, then buckets in order QUICK-FIX -> REROUTE -> ASSIGN. The streak line goes near the top so it is visible every run.

## Named exceptions

| Name | Raised when |
|------|-------------|
| `ServiceNowUnreachable` | API host does not respond |
| `ServiceNowAuthExpired` | 401 from the API |
| `RosterEmpty` | Manager-app DB returns zero active assignees |
| `RerouteTargetUnknown` | Heuristic flagged REROUTE but no target group could be inferred (becomes REROUTE-UNKNOWN in the report; not a fatal abort) |

These bubble up to the user with a clear remediation line; they do not silently degrade the run.

## Persistence seam

The solutions store and streak file live behind a small seam (`load_solutions`, `save_solutions`, `load_streak`, `save_streak`). Match logic and report rendering call the seam -- they do not read or write the JSON files directly. This is what lets the store move to SQLite or the manager-app DB later without rewriting the skill.

## Phase 1 vs Phase 2 reminder

This skill is owned by Jeremy in Phase 1 (current). The real Phase 1 work is **inbound routing cleanup** -- reducing REROUTE counts to zero over 30 consecutive days. Triage is the symptom; misrouted tickets are the cause. When the streak hits 30, Phase 2 starts and ownership moves to a named Lead/Senior. See `triage-servicenow.feature.md` -> Ownership section.
